# Independent worth of an optional artist skin finish

**Conditional A: the retained images justify defining one narrow optional SDK artist-choice contract. They do not justify changing the default or claiming a generally improved skin material.** The decision can change from “edit a private preview's active material field” to “deliberately request and accurately report one of two existing finishes.” This is useful customization rather than a proved defect fix. No API implementation, new render, material construction/setter, import or native admission follows from this value note.

I re-viewed all four unchanged archived1440×1000 PNG originals at original detail during this gate: original-front, candidate-front, original-oblique and candidate-oblique, in `skin-finish/archive/capture/`. The candidate's small exposed upper-chest highlight nearx739–782,y951–978 is less dominant. The front cheek patch nearx733–778,y632–679 and the oblique nose bridge/tip nearx508–548,y648–704 are quieter. The candidate still has a readable nose silhouette, cheek turn and jaw boundary; I do not see an obviously flattened face at this viewing size. This remains a small, composition-specific preference. Broad facial brightness, coarse hair strips, jagged tee neckline and different brow/hair samples remain. Most forehead is covered. No exclusive changed-pixel attribution, skin defect, physical calibration, moving appearance or complete forehead result is claimed.

The actual state responsibility is unusually small and explicit. All eight retained before/after states describe the same body-owned SkinNodeMaterial, sixteen mesh/material bindings, head transform, maps, roughness/normal nodes, named skin uniforms and attached Sage/lavender g050 recipe. Their recorded active clearcoat is0.34/0.12, fixed clearcoatRoughness0.24, useClearcoattrue, with clearcoat/roughness nodes and maps null. Paired cameras agree. Each before/after state is identical; across arms the fixed state differs only in active clearcoat and declared arm/view/camera. Retirement restores0.34 and records Avatar disposedtrue/leaked[], page/browserclosed. This is recorded state evidence, not independent GPU-uniform, pixel-phase or physical proof.

There is a real interface distinction, not a missing shader capability. `SkinMaterial.js:945–947` already documents and merges `options.settings` over SKIN_DEFAULTS. At1029–1030 it assigns secondLobeWeight/secondLobeRoughness to actual clearcoat fields; at1062 it retains those construction settings. `applySkinMaterial` at1301–1328 binds only the actual figure.body. `Avatar.swapFigure` at3052–3057 constructs that material with maps but no finish override; `applyShading`3234–3235 installs and retains Avatar.skin. The full preserved private preview instead mutates active clearcoat after creation, so its skinSettings.secondLobeWeight intentionally remains0.34 even in the0.12 arm. That prototype is not evidence that a new Avatar option or saved setting already works. Current inspected Avatar create/session/skin construction and Showcase settings expose no corresponding finish option; no global API-absence claim is needed.

The lowest-risk new responsibility is **creation-only, two named artist choices** with omitted/Original behavior exactly preserving0.34 and fixed roughness0.24. A softer choice can map literally to0.12. Its name must describe a quieter second lobe, not “realistic,” “correct,” “matte,” or a roughness change. Keep actual requested/attached settings, active field and construction metadata coherent through the existing figure rebuild path; record the real body owner and disposal. A live setter, arbitrary scalar range, UI/schema/import/export integration, new hue/texture/region work and more preference pictures are unnecessary for this first contract.

One reporting obligation is material: `Avatar.report()` around2600–2631 defines lighting.calibrated as comparability with previously judged numbers and derives it from exposure, ambient, environment and non-Neutral lighting. It presently assumes the fixed material calibration. A nondefault finish must not silently inherit that historical comparison claim in an ordinary Studio configuration. The later contract should explicitly exclude/qualify nondefault finish from that calibration flag or decline the new API. This is a prospective reporting responsibility, not evidence that the current untouched Avatar report is wrong. The current Neutral prototype is already outside that calibration flag.

Two alternatives and tradeoffs:

- **A — define and then separately qualify this small SDK artist choice.** Preserve the original/default branch, map only the literal0.12 option to the existing material factory setting, report requested and actual ownership/fields honestly, and retain exact skin maps, region roughness, optics and all other shading. This removes private post-construction mutation for a useful softer-highlight direction. It costs input validation, rebuild/report/lifetime checks and explicit documentation. Functional API support would still not be a recommendation across lights, bodies or motion. **Conditionally recommended for the next contract, not adopted here.**
- **B — keep the isolated preview and current0.34 only.** No additional public input or reporting burden; preserve the historical calibrated default and defer wider finish support until room/motion evidence is artistically warranted. This is safer if the implementation cannot keep the narrow promise, but leaves the visible current-composition choice accessible only through a private preview. Do not answer that by replaying the expired Kitchen fixture or tuning another value.

The preceding skin-lighting value note explicitly left Kitchen's different face modelling unanswered. That remains true. The earlier visual decision required further lighting/motion review before promoting a generally preferred production finish; this note does not waive that limit. A documented opt-in artist parameter with truthful context limits is a narrower functional promise. If “supported” would imply broadly preferred/calibrated skin or automatic Showcase/save compatibility, choose B instead.

The smallest next decision is a literal input/default/rebuild/report/owner contract, bounded to at most15minutes source design before any production edit. It must resolve the calibration field and exact default behavior without another source inventory. Later implementation, meaningful default/invalid-input/rebuild tests and actual public-owner confirmation require a fresh independent source/runtime plan; a finite maximum40-minute slice and first observed failure stop are sufficient if root chooses it. Do not reopen the old private preference pair, room fixture, scalar search or renderer/sampler/phase chain. This gate stops now with conditional A; full AAA/representation/expression/wardrobe work stays open.
