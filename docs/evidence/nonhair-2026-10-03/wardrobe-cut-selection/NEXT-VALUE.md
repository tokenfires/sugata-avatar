# Independent Wardrobe cut-selection value

Worth one bounded usable slice: expose **Hair cut — Chin-length bob / Long bob** independently of the two whole starting looks. This is a missing direct composition control for already supported combinations, not a claim that the starter links malfunction or that another hair asset/geometry experiment is admitted. It returns useful customization to the roadmap while keeping all accepted assets and closed research lines intact.

I read current showcase HTML/JS, presets/settings, colour editors, ViewerFraming and the full roadmap. The actual retained 1440×1000 `mobile-toolbar/archive/capture/desktop-portrait.png` shows starter cards at approximately x1008–1378, y334–448, Outfit at y502–545, and Hair colour at y835–883, with no independent haircut chooser. The visible current casual tee/portrait is a concrete composition a user may want to keep while comparing the longer cut. I also viewed the actual 657×868 `packages/testbed/src/palette-references/elegant-ecru.png`: the longer bob is shown with blouse/skirt. This older Studio reference has different light/material context; it demonstrates an available authored cut, not a matched current comparison or a quality advantage. Existing stippled/broad-strip hair and garment limitations remain visible and are not addressed by this feature.

The source witness is `showcase.js:200–207`: starter links clear search and preserve style, garment overrides, hair base/tint and scene, but omit outfit, framing and light. `showcase-presets.mjs:7–11` couples the two starter IDs to different cuts and outfits; lines 36–52 already support either preset with either current outfit, frame and light. `showcase-settings.mjs` can roundtrip those combinations strictly. A user can currently choose the other starting look and then restore Outfit/Framing/Light manually; the new control makes that composition direct without changing the supported schema.

Select alternative A: two explicit Hair cut choices before Outfit, fresh owned preview via the existing settings URL, exact applied settings preserved except the existing preset-to-hair selection. Refresh from the actual attached hair report. Preserve base/custom clothing colours, hair base/tint, outfit, framing mode, scene and its applicable light, and existing seed/quality/foundation contract. Selecting the already attached cut should do nothing. Guard unavailable/busy/export states using the current control ownership. State that a cut change opens a fresh preview: free orbit, live motion/pause state and unapplied drafts retain existing reload behavior. Preserving framing mode does not promise identical fitted Portrait zoom: ViewerFraming measures the new cut's head-region support.

There is one consequential semantic correction alongside this choice. `showcase.js:219` currently marks a starter card current solely from `selected.preset`. With independent long-bob/casual selection, that would mark the full After hours starter despite its blouse/skirt not being worn. The actual current cut should have its own pressed state; a starter card should be current only when the selected preset and outfit match that starter pair. Existing whole-starter links keep their behavior. This avoids presenting two different meanings of selection as if they were one.

Two concrete alternatives and tradeoffs:

- A separate cut fieldset retains whole-starting-look shortcuts and exposes the supported composition directly. It adds one small control group and requires attached-cut versus starter-pair semantics plus fresh-preview behavior to be explicit. This is preferred.
- Keep the existing starters and explain that they change cut/outfit and reset framing/light; users then restore the desired Outfit/Framing/Light controls. This is smaller and avoids another group, but keeps a multi-step workaround for a supported combination and makes direct cut comparison awkward.

The bounded research decision is whether cut changes in both directions reconstruct the same actual supported clothing/colour/scene/framing recipe except `hair`, so the new control can be shipped for composition. One finite native packet in a separately declared at-most 25-minute slice is sufficient: Studio-neutral/Portrait/casual and Kitchen/Full-look/elegant cases across desktop/mobile; actual attached report and complete exported JSON; one actual JSON reopening; no named-look storage write; old-owner retirement; current-cut no-op and busy/export/unavailable guards; actual original UI views for both choices and corrected starter states. Use existing reports and settings semantics rather than a new material-graph oracle. Stop after one failed gate or the fixed deadline; no native retry, AA/history selection, geometry/fit/material edits or widening of the contract.

The actual rendered views may establish that the selected combination is present and inspectable in these cases, not that one cut is prettier, naturally dyed, motion-qualified for every outfit, representative of broader identities or AAA complete. A separate aesthetic/character preference cannot be inferred from this control packet. Root's proposed narrow configuration/reopening question is worth doing as this feature's acceptance boundary; no broader visual claim is needed to justify the usable output. Future curated examples remain a distinct design deliverable.

No product source, asset, browser, GPU, native or generation job was changed or launched in this value review. The two original images above were actually viewed.
