The smallest useful implementation is a pure helper plus a pinned offline admission fixture, with at most 15 minutes total and one finite CPU audit. It should take the expected origin, actual Vite dev root, repository root and a declared expected file identity. Scope it explicitly to this POSIX/macOS installation and ordinary same-origin filesystem or dev-root file routes. An observer must refuse unsupported virtual/module/proxy/remote URL classes rather than infer a disk file. `/` needs an explicit declared index-file rule; hash/query handling must be declared separately from file identity. Fragment presence still needs a later source/served check and cannot be proved by path resolution alone.

Pin the installed Vite producer/resolver source, package version, config and retained fixture report. Test exact canonical absolute identities and current bytes for both retained filesystem routes and ordinary dev-root files, including the documented failure. Add finite offline cases for a filename containing spaces, percent decoding once, a fragment/query, foreign origin, malformed encoding and an unsupported route. Do not claim untested encoded-separator, Windows, symlink/public-directory or proxy equivalence. Reject ambiguous cases. Preserve completed observations on failure. Stop on any source-versus-fixture disagreement or unsupported route; do not extend into browser delivery, server restarts or a general Vite resolver. CPU mapping acceptance is not HTTP content or HTML layout acceptance.

Two alternatives have clear tradeoffs:

- A shared narrow source-qualified helper and offline fixtures make the exact defect reviewable once and prevent copied slicing assumptions in later tools. This takes a small tooling slice and requires version/scope pins when dependencies or URL classes change.
- Future observers can avoid generic resolution and use an explicit URL-to-pinned-file manifest for only their declared links and media. This is simpler and makes unknown routes fail immediately, but each packet must supply its finite URL inventory and maintain that correspondence.

I prefer the shared helper if at least one future HTML observer is planned; otherwise the explicit manifest is enough and avoids tooling for its own sake. Neither alternative authorizes another capture, fixes the closed observer or changes the character/product.
