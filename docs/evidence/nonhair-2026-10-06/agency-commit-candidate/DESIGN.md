Proposed commit-time bookkeeping contract (source proposal only)

Usable improvement: the two already witnessed obsolete-completion request/store faults and false preference honour/outgoing history. Decision: choose the smallest source interface that records only actual successful outfit application while preserving historical application and existing newest-valid-request Wardrobe loading policy.

Preferred proposal: additive `dress(garmentIds, {onApplied = null} = {})`, retaining the existing Promise<stats> result. Validate callback null/function before advancing any dress token. Existing outfit validation, floor union, loader failure, latest valid token and stats shapes stay intact. After `#applyOutfit` and lastDressMs, compute stats once; invoke onApplied(stats) once synchronously, then return those stats. Never call it for rejected validation, failed loading, disposed loading or the obsolete-token branch. Return value is ignored, so this is a synchronous notification, not an awaited work hook. Callback errors reject the dress promise after the outfit has committed; callers must not infer rollback. Internal Agency callbacks are synchronous and use existing persistence/error semantics.

Agency pin captures its requested IDs (valid arrays copied), calls dress with its synchronous callback, and moves mode/pinnedOutfit/currentRequest/pending/persist bookkeeping entirely into that callback. It still returns the stats result. An obsolete pin continuation performs no policy writes.

Agency #apply copies the chosen requested IDs before loading, sets a local applied flag only in the commit callback, and in that callback marks the actual preference honoured, records the same request-keyed outgoing history/clock as today, assigns the committed request and persists. After await it only returns the applied or superseded result. A genuinely applied preference retains honour even if a newer outfit commits before its promise continuation; an obsolete request never receives honour. Existing default pinned, ask/confirm, mood/return periods and floor policies remain. No Agency generation counter or future-mode cancellation is introduced.

Research question: can this single synchronous ownership point preserve correct current and outgoing records under (a) original two overlaps, (b) genuinely applied old request then newer pending/failing load, (c) genuinely applied old request then newer success before old Agency continuation, and (d) invalid newer request before token advancement? Stop on any failed source or first actual gate; no parameter/capture/observer rescue. Use actual rig/assets and controlled loader gates; any deliberately delayed caller continuation is a disclosed fixture scheduling seam, not an extra observed product defect.

Alternatives: immutable applied receipt plus current-applied-token predicate is explicit and avoids a callback API, but late continuation still needs chronological outgoing-history reconciliation across already committed outfits. Serialization is easier to reason about, but delays a newer wearer request and changes newest-valid-wins behavior. Withhold implementation if callback errors/reentrancy/compatibility cannot be precisely owned within the bounded slice.

Meaningful candidate gates: original slow consider/newer pin; old pin/newer pin; serial genuine honour; invalid newer pin while old load pending; failed valid newer load while old obsolete; failed valid newer load after an old actual commit; both actual commits before older caller continuation; callback once/never/throws and input alias capture; existing unmodified agency serial assertions and CatalogueDresser integration. No pixels, geometry fit, animation, performance, human data or AAA acceptance. Entire actual probe stays frozen and is not rerun.

Candidate isolation proposal: exact canonical Wardrobe/Agency source text in this leaf; an explicitly recorded two-relative-import projection lets the candidate Wardrobe reuse unchanged GarmentInterior/StyleOptions. Agency requires no rewiring. A new meaningful regression entrypoint imports these candidates, plus a projected existing serial selftest retaining every original assertion. No production file changes until a passing candidate and independent actual review/root verification. Inputs/commands/jobs/hashes/projection rules and limits recorded before invocation. Existing accepted assets/defaults/frozen references/wider roadmap remain.
