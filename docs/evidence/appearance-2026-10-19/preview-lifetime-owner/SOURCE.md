## API and ownership boundaries

`createPreviewLifetime({parentSignal,limit})` supports a same-realm standard AbortSignal and1–64lifetime resource identities; default64. Its frozen API has `signal`, `checkpoint`, `create`, `release`, `waitData`, `publish`, `close`, `inspect`. There is no reset/reopen/epoch search. Close commits terminal state and first reason before any callback, removes the owned parent listener, attempts native abort, then attempts remaining releases in reverse registration order. Repeated close is effect-idempotent and returns a fresh snapshot; a reentrant snapshot can honestly have `closing:true` and pending releases.

Factories, disposers and publication callbacks must be synchronous, bounded and controlled by the client. Creation is guarded before factory invocation; an in-flight slot reserves capacity across synchronous reentrancy. Values must be new non-null resource objects/functions; a native Promise result is refused, but the owner cannot generally diagnose/stop arbitrary asynchronous factories, callback internals, foreign thenables or private constructor allocations. These are outside the protocol. A factory may reenter close and return a completed resource; the owner records/attempts its release immediately and throws the lifetime error rather than returning the value. A throwing factory's original error propagates; its private partial allocations remain outside ownership.

Each identity is registered only once for the entire lifetime, even after explicit release. Release attempts are marked before callbacks. An explicit failed release propagates the original thrown value, including undefined, and is recorded. Close contains release failures and continues through the remaining entries; no automatic retry. Counters mean attempts/pending attempts, never proof a throwing disposer actually freed a resource. `release` during the close drain returns false so a reentrant callback cannot reorder the reverse drain. Later completed factory resources are separately attempted once. Failure records remain exposed in copied/frozen snapshots; parent-detach failure is explicitly `failed`, not a successful removal certificate.

The parent listener observes actual `aborted` state, rather than trusting a forged abort event, and is explicitly removed on close. Entry/post-await checkpoints also observe actual parent state. Native signal event notification supplies ordinary prompt closure; hostile replacement/suppression of standard event methods/listeners and arbitrary external callback exceptions are not general cancellation guarantees. Own native AbortSignal reason follows the first close reason. No asynchronous callback can reopen this owner.

`waitData` accepts data only, not a promise of a resource to own. It attaches both settlement handlers even if already closed, then checks terminal authority before waiting and after settlement. Open rejection preserves the original value; closure wins over later fulfilment/rejection. It does not cancel or immediately settle an already pending non-abortable data operation, which may remain pending until its own settlement. Callers must use guarded `create`/`publish` after a wait because closure can occur between promise continuations. `publish` guards synchronous callback invocation and refuses its result if the callback reentered close. Already-started callback side effects cannot be undone. Clients bypassing this API remain unqualified.
