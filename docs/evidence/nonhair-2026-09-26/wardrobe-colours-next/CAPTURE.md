# Fixed colour examples and unchanged controls

The first native feature triplet stopped at an unequal returned-default PNG. A separately
labeled unchanged old-code repeat also failed the same exact image gate. Both rejected packets
are preserved; no tolerance, product setting or qualification claim changed. The actual
geometry and declared rendered histories agree. A cause for the remaining pixel variation
has not yet been established. See `RENDER-REJECTIONS.md` and independent critique.

The product implementation is separate in the managed custom-colours worktree.
`capture-colours.mjs` derives its clock,
state, response-binding and retirement path from the completed skin A–B–A controller. It uses
the unchanged `createMicroCapture` helper with body micro-normal scale always 0.25; this study
does not change skin. The shared explicit frame epoch and temporal reset are diagnostic
conditions, not ordinary idle cadence.

Four groups use the native Front and Back buttons for each existing outfit in Kitchen,
body framing, seed 20260807, viewport 1100×1000 and DPR 1. Each later group contains three fresh
pages: unchanged base, custom example, returned base. Colours are supplied through the new
creation-time URL/configuration path; no live material or colour-node replacement is injected.

| Outfit and base | Custom example | Unchanged parts |
| --- | --- | --- |
| Casual / Ecru | Top `#617a70`, shoes `#383a3f` | Denim and socks keep Ecru |
| Elegant / Charcoal | Top `#cbbbad`, bottom `#3d5054`, shoes `#4b3639` | Socks keep Charcoal |

These are fixed review examples, not proposed new starter presets or certified colours.
The outfit's accepted cut remains fixed throughout each group. A separate `--capture-base`
mode takes only the four unchanged controls before integration. Its report explicitly labels
that scope and cannot claim custom-colour qualification. Later integration requires an explicit
comparison of those four pre-feature state and PNG hashes against their post-feature base
counterparts, bound to both sealed packets. The triplet controller does not currently enforce
this cross-packet admission; its fresh base/return equality alone cannot prove old defaults.

The complete run requires actual exported settings and attached appearance metadata to match
the declared optional colours. All body/worn topology, draw masks, CPU-skinned geometry, rig,
morphs, camera, native physical groom state and body-material/grade values must agree within
each triplet. The original helper supplies 64 zero-time public updates and one native Save image
draw. All actually rendered temporal/grain phases must match, and the returned base PNG must be
byte-identical. The custom PNG must differ; that condition alone does not prove every part is
correct or attractive, so material tests and direct image review remain necessary.

The controller preserves raw warnings, bound actual asset responses, source archives, original
download bytes and exact state artifacts. It restores only its own capture wrapper and the
already unchanged micro-normal value immediately before the original nonpersisted pagehide
handler. Disposal is an explicit handler fixture; actual navigation and the new form's behaviour
need a separate focused UI pass. No failed state is allowed to earn acceptance by lowering a
threshold or changing these sample colours mid-run.

The full feature also needs desktop/mobile draft and Apply checks, default/reference clearing,
Original refusal, actual JSON/named-look reconstruction, mixed-outfit mapping, preserved scene
controls and ownership checks. Kitchen front/back colour plates do not qualify other lighting,
all RGB choices, motion, garment fit, skin, hair or representative character quality.
