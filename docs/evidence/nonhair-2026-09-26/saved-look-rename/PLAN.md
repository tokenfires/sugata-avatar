# Rename a saved look

Current Wardrobe rows offer Open and Remove only. Changing a name currently requires saving another entry and removing the first, cannot start at the 12-entry limit, and risks losing the original entry's configuration. This slice adds an explicit metadata-only Rename action.

`SavedLooks.rename(id, name, expectedItem)` reads the latest collection, requires the selected item to match its displayed snapshot exactly, and uses the existing strict snapshot commit. It preserves ID, position and the complete configuration, including unavailable configurations. Existing trimmed 1–40-code-point names and NFC/case-insensitive duplicate rules apply, excluding the selected ID. An exactly unchanged trimmed name performs no write and preserves removal Undo; a successful real rename clears old Undo. Failures keep stored bytes and Undo. Rename refuses configurations containing nonfinite numbers or numeric negative zero anywhere in the retained list, including no-op requests, because the existing serializer cannot preserve them; those entries stay stored. This is latest-read protection, not an atomic multi-tab transaction claim.

Each row gets Rename, including unavailable entries and a full collection. A separate labeled modal contains the current name, Save, Cancel and visible error feedback. Enter submits; Escape and Cancel close without writes. Busy or unavailable collection states disable Save; Cancel remains usable. A read failure exposes Retry saved looks, which rereads storage without discarding the draft or reloading the viewer. Storage events preserve the draft, reread the list and explicitly refuse saving a changed/removed selected entry. Unrelated edits remain preserved by the latest-read mutation. Closing returns focus to that row's Rename button, or the Saved looks summary when the row is unavailable.

No look is applied and no viewer operation is called. The avatar instance, configuration, motion clock, camera and attention state stay under their existing owners. Existing sticky layout, settings, navigation and lifecycle flags remain intact.

Focused CPU cases cover name validation/NFC duplicates, own-name case changes, 12-entry capacity, unsupported configuration preservation, exact no-op/write counts and Undo, stale selection/removal, unrelated latest edits, read/access/commit-read/write failures and commit-time races. A later coordinated native check should exercise real modal keyboard/focus, plain-text names, retry/cancel, full capacity, storage events and unchanged fixed-clock viewer/attention state on desktop/mobile. No native result is claimed by CPU work.
