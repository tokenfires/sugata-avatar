Rename reads the latest list and checks the displayed item's complete snapshot before changing anything, including before an apparent no-op. The selected ID is excluded from duplicate-name comparison, so changing only its letter case is allowed. Other IDs, list positions and parsed configurations are retained, including ordinary unsupported future configurations and unrelated edits already present at the latest read. Renaming uses no additional collection slot, so a full list can still be renamed. Existing name validation uses trimmed 1–40 code points and an NFC-plus-lowercase duplicate key; it is not a new locale-specific naming policy.

An exactly unchanged trimmed name performs no write and keeps removal Undo. A real successful rename clears Undo only after commit. Name errors, stale/missing selected items, storage access/read/write failures and detected prewrite interleavings leave storage and Undo untouched. This is the existing latest-read/prewrite comparison discipline, not an atomic cross-tab transaction guarantee. Serialization can change envelope formatting/key spelling, so this is parsed configuration preservation, not byte-identical JSON formatting after a successful edit.

I found and reproduced a concrete gap in the first implementation: a retained raw configuration containing JSON `1e400` parsed as Infinity and was silently rewritten to null by a name change. The same serialization could collapse an old unsafe snapshot into a later null/zero value and miss a stale-item change. This inherits a general serializer limitation, but contradicted Rename's new metadata-only contract. The narrow correction scans all retained configurations **and the expected snapshot** before comparison, copy or commit, refusing nonfinite numbers and numeric negative zero. It keeps those raw entries readable/stored and refuses Rename without writes or Undo changes, even for an apparent no-op. It does not claim to repair other collection actions or recover original numeric lexemes already rounded by JSON parsing. Exact rejected source and red witnesses are retained.

The modal uses a named dialog, labeled prefilled/selectable input, Save/Cancel, visible alert feedback, native Enter submission and native Escape close. Cancel stays available during busy/read-failure conditions. Read failure exposes an explicit retry without throwing away the draft; external storage updates preserve the typed text and disable a stale selection until the user cancels/reopens. Successful close targets the current row's Rename button or the saved-list summary if the row is unavailable. Rendering names with `textContent` and text-valued attributes avoids interpreting them as HTML. No new Avatar, camera, attention, motion, navigation or material operation is called by Rename.
