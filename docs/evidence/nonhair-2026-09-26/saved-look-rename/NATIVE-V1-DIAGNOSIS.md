# Rejected first native Rename run and bounded successor

The first production-page run stopped before the first Rename group. This is not evidence of a Rename product failure or acceptance. The exact rejected report, manifest, controller and first-page screenshot are preserved in `rejected-native-v1/`; `receipt.json` binds the lossless copies and source witnesses. The complete original capture/source archive remains in `captures/saved-look-rename-2026-09-26/native-v1`.

There are two separate network observations:

- Thirteen `blob:http:` responses were wrongly sent through the controller's HTTP-path allowlist. Three's pinned `GLTFLoader.loadImageSource` creates these internal URLs from embedded image bufferViews, then `ImageBitmapLoader` fetches them. The six required GLBs contain 13 distinct PNG image payloads (body 6, casual 3, shoes 2, bob02 2). The matching count alone does not prove URL-to-image provenance: v1 never read the blob response bytes.
- The ordinary HTTP request `/assets/g050-yiqsxV00.glb` reported `net::ERR_ABORTED`, and DevTools could not provide its body. This built file is the exact accepted `assets/hair/bob02/g050.glb`, 3,347,176 bytes, SHA256 `a666a80777f0b93a824857dc2e2cbffe27cd2c8991a3f4ec8215ebc1d94298bd`. V1 has no successful observed hash for it. This failure is not explained or waived by the blob correction.

The source path awaits native `FileLoader` stream completion and `Response.arrayBuffer()` before `GLTFLoader.parse`, which resolves before Avatar publishes the attached groom. The ready screenshot shows the current avatar with hair. No default hair-load abort call was found in the inspected Avatar path; its token checks discard superseded results without aborting the HTTP request. Those facts do not prove the actual request completed successfully. V1 has no request IDs, initiator/transport completion events, byte totals or server completion timeline, so it cannot distinguish a transport/read failure from an observation discrepancy. No hair loader, renderer, asset or product source is changed.

V1 also inserted the owner record after the failing network drain. Thus `owners: []` coexists with one actual clean retirement: disposed, no leaked handles, null Stage ownership, and all tracked renderer memory zero. Its `cleanupFailure` repeats the earlier network error assertion; the recorded retirement itself succeeded.

The successor controller makes only these instrument corrections:

1. Keep HTTP responses same-origin, manifest-addressed, exact-status and exact-body-hash. Request failures and unavailable HTTP bodies remain fatal. Server-sent bytes never substitute for browser-observed bytes.
2. Admit a blob only after its actual browser response has status 200, MIME `image/png`, and exact length/hash matching a validated embedded image view in a pinned required GLB. Retain all candidate parent witnesses when image bytes coincide. At drain, at least one matching parent's actual exact HTTP body must have been observed in the same owner phase. Unknown/changed/external blobs fail; no arbitrary blob exception exists.
3. Record native Playwright request identity/timestamps and passive CDP request/initiator, response, data, finish/failure events. Record the static server's separate sent hash, response finish/close and incoming abort timeline. These are diagnostic facts, not a replacement success criterion. No fetch, stream, Response, loader or browser API implementation is wrapped.
4. Register each published native owner and teardown observer before warm draws or network drain, with `qualified: false` until admission succeeds. Require every registered owner to retire exactly once even after failure. Drain pending observations during cleanup without rethrowing old measurement errors as a second disposal failure; all errors still prevent overall completion.

Eight focused CPU groups cover protocol/origin separation, exact blob bytes/type/length, malformed or changed GLBs, same-phase successful parent requirement, the actual pinned 6-GLB/13-image catalogue, and the original-request event chain including missing/failed/duplicate/redirected events. These are instrument tests, not a browser result. A fresh native run is still required. If the unexplained HTTP failure repeats, the gate stops before UI checks and preserves the new trace for diagnosis; no exception or product change is authorized by this proposal.

The initially reviewed but unlaunched successor used Playwright `response.body()`. Its exact controller/helper/test bytes are preserved as `rejected-native-v1/unlaunched-response-body-v2*`. Read-only review of the installed default Playwright 1.61.1 showed that method can issue an auxiliary `Network.loadNetworkResource` fetch after an empty DevTools body. There is no evidence that this fallback caused v1. The final successor instead attaches CDP before each page navigation and reads each original request ID with one direct `Network.getResponseBody` only after `loadingFinished`, with no refetch fallback. Explicit 204s require no body. Each session ledger rejects missing responses/finishes/body results, duplicate or reused IDs, redirects, failed loads and bounded body-read timeouts.

The final manifest binds the actual existing selected Playwright entry, package versions, bootstrap and core bundle. Resolution follows the same candidate order as MotionProbe and imports without launching; the existing supported override then selects that same admitted entry during the run. These relevant host sources are archived and rechecked, but are not described as a complete transitive host dependency archive. No browser install, dependency or launch flag is changed. Server completion remains separate evidence, never proof of original browser consumption.
